# Issues и PR

Доска **Issues и PR** — отдельная страница со списком issues и pull request проекта из GitHub, GitLab, Gitea, Forgejo или Gerrit (на GitLab это merge request, на Gerrit — changes; issues в Gerrit нет), либо ваших issues из Linear. Выберите элемент — его предпросмотр откроется рядом со списком. Если здесь вы смотрите другой проект, остальное приложение остаётся на своём.

## Открыть доску

- Нажмите значок pull request в заголовке боковой панели, рядом с запланированными задачами и архивом.
- Выберите **Issues и PR** в палитре команд.
- Нажмите <kbd>⌘K</kbd>, а затем <kbd>B</kbd> (<kbd>Ctrl+K</kbd>, а затем <kbd>B</kbd> в Windows и Linux). Те же клавиши закрывают её.

На телефоне коснитесь кнопки pull request внизу меню сессий. В расширении VS Code доски нет.

Доска открывается на том проекте, вкладке и команде, где вы её оставили.

## Поиск элементов

Всё умещается в одной строке панели инструментов. Слева — выбор проекта со значками и поиском. Рядом переключатель **Issues**, **Pull requests** и **Linear**. Issues и pull request берутся из хостинга проекта: GitHub, GitLab, Gitea, Forgejo, Gerrit или хоста, добавленного [расширением](/ru/extensions/#расширение-как-git-хост). Вкладка **Linear** появляется только после подключения Linear. Если у проекта нет подходящего хоста, видна только она или сообщение, что показать нечего. Remote с псевдонимом хоста из `~/.ssh/config`, например `github.com-work`, не распознаётся как один из перечисленных хостов.

Второй список рядом с выбором проекта появляется, если папка содержит несколько репозиториев, и определяет, какие элементы показывает доска. Если сама папка не является Git-репозиторием, но содержит вложенные репозитории, первым вариантом и вариантом по умолчанию будет **Все репозитории**: issues и pull request всех репозиториев GitHub показываются вместе, с именем репозитория в каждой строке. Поиск работает по всем, включая вставленную ссылку или номер. Примечание над списком показывает, сколько репозиториев не включено — например, на GitLab, Gitea, Forgejo, Gerrit или недоступных подключённым аккаунтам. Через меню можно узнать, какие именно и почему. Выберите один репозиторий, чтобы видеть только его.

Если папка сама является Git-репозиторием, он показан первым и выбран по умолчанию, а его субмодули и вложенные рабочие копии доступны рядом. Вариант **Все репозитории** здесь не предлагается, чтобы элементы корневого репозитория не дублировались. Доска запоминает выбор отдельно для каждого проекта, независимо от репозитория, выбранного в представлении Git.

Комментарии, метки, рецензенты и слияние относятся к репозиторию самого элемента. **Новая сессия** по-прежнему запускается в папке проекта. **Изменения** и **Walkthrough** открывают pull request в его репозитории и не меняют выбор в представлении Git. Начать работу с такими элементами в worktree пока нельзя. Ссылка на issue или pull request открывается в Tracker и загружается через его собственный репозиторий. На телефоне она открывается на доске через тот же репозиторий, не меняя список. В расширении VS Code доски нет, поэтому это поведение его не затрагивает.

В **Linear** список проектов превращается в выбор команды: **Все команды** или одна команда. Если для проекта доступен только **Linear**, список проектов остаётся рядом со списком команд, чтобы можно было сменить проект. Если подключено несколько рабочих пространств Linear, переключайтесь между ними в том же меню. Подключение Linear описано в разделе [Интеграции](/ru/integrations/).

Поиск принимает название, номер или вставленную ссылку. Меню фильтров не закрывается, пока вы выбираете, поэтому фильтры можно сочетать. На GitHub поле поиска также принимает его операторы (`is:closed`, `label:bug`, `author:@me`); они имеют приоритет над выбранными пунктами меню.

Для GitHub, GitLab, Gitea, Forgejo и Gerrit:

- Статус: **Open**, **Closed**, **All**, а для pull request ещё **Merged**
- Люди: **Anyone**, **Assigned to me**, **Created by me**, а для pull request ещё **Review requested**

В меню **Фильтр** также перечислены метки репозитория с поиском и галочкой для каждой. Любая выбранная метка сразу сужает список. Фильтр сохраняется отдельно для каждого репозитория и вкладки.

Для Linear:

- Статус: **Open**, **All**, **Backlog**, **To Do**, **In Progress**, **In Review**, **Done**, **Canceled**, **Duplicate**
- Люди: **Anyone**, **Assigned to me**, **Created by me**
- Приоритет: **All priorities**, **Urgent**, **High**, **Medium**, **Low**, **No priority**

## Просмотр элемента

В предпросмотре видны описание, метки и комментарии. В issue из Linear нажмите на значок статуса, чтобы перевести его в другое состояние команды.

В строке **Метки** есть кнопка с карандашом: она открывает список меток репозитория с поиском. Отмечайте нужные и снимайте отметки. Изменение сохраняется, когда вы закрываете список, поэтому несколько нажатий считаются одним изменением. У открытого pull request (на GitLab — merge request) есть ещё строка **Рецензенты**, которая работает так же: в ней люди, которые могут делать ревью в репозитории. На GitHub автора pull request в списке нет. У issues из Linear нет ни той, ни другой строки.

Карандаш рядом с заголовком позволяет одновременно изменить название и описание. <kbd>⌘</kbd>+<kbd>Enter</kbd> сохраняет изменения (<kbd>Ctrl</kbd>+<kbd>Enter</kbd> в Windows и Linux), <kbd>Esc</kbd> отменяет их, после чего предпросмотр показывает сохранённое на хосте содержимое. У элемента, открытого по ссылке, карандаша нет, как и у хоста, который не разрешает менять текст.

В issues и pull request на временной шкале перечисляются элементы, которые на них ссылаются: кто и когда упомянул элемент, а также метка-ссылка (между репозиториями — `owner/repo#42`), по которой его можно открыть. У обсуждений такого списка нет: GitHub не предоставляет для них временную шкалу. Эти строки показываются для GitHub, GitLab, Gitea и Forgejo, а также для хостов из расширений, которые передают такие данные. В Gerrit они отсутствуют.

## Комментарии и ревью

Под активностью issue или pull request есть поле комментария. **Comment** публикует ваш текст на GitHub или GitLab, так же как <kbd>⌘</kbd>+<kbd>Enter</kbd> (<kbd>Ctrl</kbd>+<kbd>Enter</kbd> в Windows и Linux). Текст остаётся в поле, пока его не опубликуют, так что при неудаче ничего не теряется. При переходе к другому элементу поле очищается. У issues из Linear его нет.

У открытого pull request (на GitLab — merge request) есть ещё **Approve** и **Request changes**, и текст из поля уходит вместе с ревью. Для **Request changes** нужен текст: напишите, что изменить. Ревью относится к коммитам, которые показывает предпросмотр: если с тех пор кто-то сделал push, ревью отклоняется, а предпросмотр обновляется, чтобы вы могли посмотреть ещё раз. На GitLab **Request changes** работает, когда вы рецензент этого merge request, а текст ревью публикуется отдельным комментарием. Если не удалось опубликовать только этот комментарий, ревью всё равно засчитано, а ваш текст остаётся в поле.

У изменения Gerrit есть строка для каждой метки проекта, например Code-Review и Verified, с доступными вам оценками. Выберите оценки и нажмите **Vote**. Текст отправляется вместе с голосами как сообщение. Голоса относятся к последнему patchset, поэтому при просмотре предыдущего они недоступны.

У написанного вами комментария рядом с кнопкой отправки есть меню: **Редактировать** изменяет комментарий, а **Удалить** удаляет его после подтверждения. Ответ на комментарий можно изменить и удалить тем же способом. Действия выполняются на хосте, поэтому изменения видны всем.

## Начало работы

Действия расположены внизу предпросмотра.

- **Новая сессия** открывает новую сессию в проекте с элементом, прикреплённым к полю сообщения. Первое сообщение вы пишете сами.
- **Открыть в worktree…** открывает диалог «Новый worktree» с уже выбранным элементом: для issue это запуск работы, для pull request — получение его ветки. См. [Сессии в worktree](/ru/worktrees/).

Для issue из Linear **Начать в** показывает проект, в котором начнётся сессия. Это проект, сопоставленный с командой issue в карточке Linear в разделе [Интеграции](/ru/integrations/). Если команда не сопоставлена, это проект по умолчанию, а если нет и его — проект, который доска показывала последним. Там же можно выбрать другой проект для этой issue.

## Pull requests

Предпросмотр pull request также показывает его ветку, размер (добавленные и удалённые строки и изменённые файлы), проверки и ревью. Лента **Activity** расставляет комментарии, вердикты ревью и самые новые коммиты в том порядке, как всё происходило. Коммиты, шедшие подряд, сгруппированы, так что видно, на какие коммиты ответило ревью.

Рядом с размером две кнопки. **Изменения** открывают дифф pull request в боковой панели, а **Walkthrough** открывает его [обзорный тур](/ru/walkthrough/). Если приложение сейчас на другом проекте, сначала оно переключится на проект этого PR. На телефоне **Изменения** открывают PR на вкладке **Git** рабочей панели; **Walkthrough** есть только на десктопе и в вебе.

Внизу **Слить** сначала запрашивает подтверждение, а затем выполняет слияние обычным для вас способом. Значок состояния рядом с заголовком открывает меню, в котором запрос можно переключить между **Преобразовать в черновик** и **Готов к ревью**, если хост это поддерживает, а также закрыть или снова открыть.

В Gerrit предпросмотр также показывает тему изменения и его режим — приватный или выполняемый. Если у изменения несколько patchset, рядом с **Изменения** появляется список выбора версии файлов и диффа; по умолчанию выбран последний. Вместо **Слить** используется **Submit**, недоступный до выполнения требований проекта, которые перечислены рядом. Действия **Закрыть** и **Открыть заново** называются **Abandon change** и **Restore change**.

То же меню закрывает открытый issue или pull request (**Закрыть issue**, **Закрыть pull request**, **Закрыть merge request** в GitLab) и открывает закрытый заново (**Открыть issue заново**, **Открыть pull request заново**, **Открыть merge request заново**). Подтверждение не нужно, поскольку действие обратимо. У слитого pull request такого пункта нет. В GitHub issue закрывается как выполненная.
