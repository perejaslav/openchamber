# Русский форк OpenChamber

Это личный форк [openchamber/openchamber](https://github.com/openchamber/openchamber)
с русской локализацией интерфейса и документации. Всё остальное — оригинальный проект,
и он продолжает развиваться независимо.

**Русский здесь — язык по умолчанию.** Свежая установка запускается на русском;
английский и остальные одиннадцать языков остаются в переключателе. Языки, которые
форк не распознал, тоже откатываются на русский.

Апстрим русскую локализацию не принял (см. «Статус pull request'ов» внизу), поэтому
форк — самостоятельный проект, а не заготовка для мержа: официальное приложение
ставится из апстрима, а русский интерфейс накатывается поверх патчем из ветки `ru`
(см. «Сборка и установка русской версии вручную»). Ветка `ru` подтягивает апстрим
автоматически (см. «Автосинхронизация с апстримом»), релизы форк больше не собирает:
старые сборки в [Releases](https://github.com/perejaslav/openchamber/releases) остались
как история.

Этот файл описывает, как устроен форк и как его сопровождать.

пользователя. `AGENTS.md` к тому же прямо требует, чтобы документация проекта была
на английском.

## Свои функции форка

### «Открыть в OpenChamber» в контекстном меню Проводника

Правый клик по папке → пункт меню → папка открывается в OpenChamber проектом и
новым чатом в ней. Пункт появляется в Windows автоматически: приложение само
регистрирует его в `HKCU\Software\Classes\Directory\shell\OpenChamber.OpenInOpenChamber`,
поэтому обновление приложения его не стирает.

| Что | Где |
|---|---|
| Вся логика функции | `packages/electron/fork/open-folder-context-menu.mjs` (форковый файл) |
| Врезки в апстримный код | `packages/electron/main.mjs` — импорт и три вызова |
| Правило «наложить заново» | `scripts/ru/fork-hooks.mjs` |
| Сторож | `packages/ui/src/lib/fork-guards.test.ts` |

**Почему это переживает мержа с апстримом.** Логика лежит в файле, который
апстрим не трогает, поэтому конфликт возможен только в трёх точках врезки. Эти
точки описаны в `scripts/ru/fork-hooks.mjs` как «якорь → замена», и резолвер
(`scripts/ru/resolve-merge-conflicts.mjs`) накладывает их на версию апстрима
автоматически — так же, как он накладывает русскую часть словарей. Если апстрим
перепишет код так, что якоря перестанут совпадать, resolve падает, синк
останавливается и открывает issue: фича не пропадает молча.

Сторож в `fork-guards.test.ts` проверяет и другое: что врезки на месте, и что
наложение поверх «апстримного» файла действительно их восстанавливает.

Патч только интерфейса (`web-dist`) эту функцию не привозит: она живёт в
main-процессе (`main.mjs` и `fork/open-folder-context-menu.mjs`). А main-патч
(`scripts/ru/install-desktop-main.ps1`, см. «Сборка и установка русской версии
вручную») её привозит: пересобранный `dist-bundle/main.mjs` включает врезки
форка. Пункт «Открыть в OpenChamber» есть либо в сборке, скомпилированной из
ветки `ru` целиком, либо в официальном приложении с накатанным main-патчем.

**Как это работает.** Приложение получает папку аргументом, а не через URL:
Проводник подставляет `%1` дословно, и путь с `&`, `#`, `?` или `%` внутри
query-строки бы сломался. Путь идёт внутри самого ключа —
`--open-folder="<путь>"`, — и это не прихоть: Electron не отдаёт командную
строку так, как её записал Проводник. Chromium пересобирает её по своим
правилам: сначала все ключи, потом позиционные аргументы, — поэтому пара
`--open-folder "<путь>"` до main-процесса доезжает разорванной, а значение
внутри ключа переживает перестановку. Дальше main-процесс регистрирует папку на
локальном сервере (`POST /api/openchamber/directory`), читает свежие настройки и
отдаёт рендереру два события, которые тот и так понимает:
`openchamber:settings-synced` (рендерер забирает список проектов и
переключается на активный) и `openchamber:open-draft-session` (новый чат в этой
папке). Код `packages/ui` при этом не меняется совсем.

**Как убрать.** Пункт меню пишется приложением при каждом запуске, поэтому
удаления ключа вручную мало — он вернётся. Чтобы пункта не было, удалите
ветку реестра после закрытия приложения:

```
reg delete "HKCU\Software\Classes\Directory\shell\OpenChamber.OpenInOpenChamber" /f
```

## Ветки

| Ветка | Что в ней | Назначение |
|---|---|---|
| `main` | `upstream/main` + копии workflow поверх апстрима | основа для автосинхронизации (там GitHub запускает schedule) |
| `ru` | **всё вместе**: локализация интерфейса и доков + русский `README` + этот файл + скрипт патча | рабочая ветка, из неё накатывается русский патч |
| `feat/ru-locale` | только локализация интерфейса | историческое: ветка закрытого PR №1 |
| `feat/ru-docs` | только локализация сайта документации | историческое: ветка закрытого PR №2 |

`main` несёт только копии workflow поверх апстрима — `ru-upstream-sync.yml`
(коммиты `e6b934956`, `b9fceba`) и бывшую копию релизного workflow (коммит
`bf818cdb5`, удалена при переходе на патчи) — других своих коммитов туда не
кладём. Поэтому
обновление `main` идёт обычным мержем (`git merge upstream/main`), а не
`--ff-only`: fast-forward после наших коммитов уже невозможен.

`feat/*` больше не нужны — апстрим оба PR закрыл. Удалять их не обязательно, но
держать в «пригодном для мержа» виде смысла нет: всё живое живёт в `ru`.

### Remote

```
origin    https://github.com/perejaslav/openchamber.git      # ваш форк
upstream  https://github.com/openchamber/openchamber.git     # оригинал
```

## Обновление до новой версии апстрима

Обычно это происходит само — см. «Автосинхронизация с апстримом». Ниже — то же самое
руками, если автоматика остановилась на конфликте.

```bash
cd openchamber

# 1. Подтянуть оригинал
git fetch upstream

# 2. Обновить основу (обычный мерж: в main уже лежат наши коммиты sync-workflow)
git checkout main
git merge upstream/main
git push origin main

# 3. Перенести рабочую ветку на новую основу
git checkout ru
git merge upstream/main
# разрешить конфликты (см. ниже)
git push origin ru
```

`feat/*` в этой схеме больше не участвуют: апстрим оба PR закрыл, поддерживать их
в пригодном для мержа виде незачем.

### Конфликты в документации

При обновлении `ru` конфликты возможны только в трёх файлах: `README.md`,
`docs/CUSTOM_THEMES.md`, `SECURITY.md` — потому что они переведены **на месте**.
Правильная сторона — ваша:

```bash
git checkout ru
git merge upstream/main
# при конфликте в перечисленных файлах:
git checkout --ours README.md docs/CUSTOM_THEMES.md SECURITY.md
git add README.md docs/CUSTOM_THEMES.md SECURITY.md
git commit
```

Если апстрим **добавил новый раздел** в README, `--ours` его потеряет. Поэтому после
такого мержа стоит заглянуть в диф:

```bash
git diff upstream/main -- README.md | head -50
```

и дописать перевод нового раздела руками.

### Конфликты в локали

В `packages/ui/src/lib/i18n/` конфликты будут почти наверняка: апстрим добавляет новые
ключи. Типичный случай — новый ключ есть в `en.ts`, но отсутствует в `ru.ts`, и тест
паритета падает с сообщением вида:

```
all locales stay in key parity with english
```

Что делать: найти новые ключи и доперевести.

```bash
# ключи, которые есть в en, но отсутствуют в ru
cd packages/ui/src/lib/i18n/messages
comm -23 <(grep -oE "^  '?[^']+'?:" en.ts | sed "s/[: ]//g;s/'//g" | sort -u) \
         <(grep -oE "^  '?[^']+'?:" ru.ts | sed "s/[: ]//g;s/'//g" | sort -u)
```

Правила перевода и глоссарий лежат в репозитории:

- `translation/UI-BRIEF.md` — интерфейс приложения;
- `translation/DOCS-BRIEF.md` — сайт документации.

Глоссарий общий и обязательный: интерфейс и документация должны использовать одни и те
же слова. Перед тем как допереводить что-то новое, прочитайте нужный бриф — там же
описано, что переводить нельзя.

## Релизы

Форк больше не собирает релизы. Старые русские сборки остались в
[Releases](https://github.com/perejaslav/openchamber/releases) как история, новых
не будет: скачиваний у них не было, а ручные сборки выходили криво — только Windows,
без Linux. Русский интерфейс накатывается патчем поверх официального приложения
(см. «Сборка и установка русской версии вручную»).

### Теги `ru-v*` больше ничего не запускают

Раньше релиз запускался пушем тега вида `ru-v*`, а отдельный workflow собирал
Windows x64 и Linux x64 и прикреплял файлы к GitHub Release. Этот workflow удалён:
пуш такого тега теперь ничего не делает, новых тегов не создаём. macOS и раньше
не собирался: без подписи Apple приложение там не запускается.

### Про версию

Версия приложения берётся из `packages/electron/package.json` и **остаётся равной
версии апстрима**; патч её не меняет. После каждого обновления официального
приложения русский патч накатывается заново: `status` покажет `STALE`,
дальше пересборка и `apply` (см. «Сборка и установка русской версии вручную»).
Маркер `.openchamber-locale-patch` ставит сам `apply`, по нему `status`
отличает патч от оригинала.

### Автообновление

Фид обновлений указывает на апстрим: `PRODUCTION_UPDATER_FEED` в
`packages/electron/updater-feed.mjs` и `build.publish` в
`packages/electron/package.json` возвращены к `openchamber/openchamber`.
Официальные обновления прилетают как обычно и привозят английский интерфейс —
это ожидаемо, патч после них накатывается заново.

### Установщик

Установщик теперь официальный, от апстрима: подписью занимается он, форк
ничего не собирает и не подписывает.

### Workflow на форке

Апстримные workflow (19 штук) на форке **отключены**: они завязаны на Blacksmith и на
секреты апстрима и только копили бы зависшие прогоны. Отключение хранится в настройках
репозитория, а не в файлах, поэтому после синхронизации с апстримом стоит проверить,
не появились ли новые включённые workflow:

```bash
gh workflow list -R perejaslav/openchamber --all
```

Свой workflow (`Fork release (RU)`) удалён — релизы форк больше не собирает.
Пуш тега `ru-v*` ничего не запускает. Включённым остаётся только `RU upstream sync`.

## Автосинхронизация с апстримом

Ветка `ru` обновляется сама: `.github/workflows/ru-upstream-sync.yml` раз в 12 часов
проверяет, не вышел ли новый релиз апстрима, и если вышел — вливает его в `ru`
без участия человека. Релизы при этом не собираются: дальше русский патч
накатывается вручную (см. «Сборка и установка русской версии вручную»).

### Что делает прогон

1. Находит последний релизный тег апстрима (`v<semver>`).
2. Пропускает работу, если ветка `ru` этот тег уже содержит.
3. Мержит тег в `ru`.
4. Приводит словари в порядок: конфликты локализации разрешаются механически,
   недостающие ключи подставляются английским текстом с пометкой «(не переведено)»,
   лишние (апстрим их больше не использует) убираются.
5. Прогоняет тесты локали и `type-check`.
6. Пушит `ru`.

### Секрет `RU_SYNC_TOKEN`

Ветку нужно пушить **от имени PAT**, а не `GITHUB_TOKEN`: мержи апстрима приносят
правки файлов в `.github/workflows/`, а пуш с такими изменениями требует права
Workflows, которых у `GITHUB_TOKEN` может не быть.

Создайте **fine-grained personal access token**:

- Repository access → Only select repositories → `perejaslav/openchamber`
- Permissions:
  - **Contents: Read and write** — пушить ветку и тег;
  - **Workflows: Read and write** — апстрим правит файлы в `.github/workflows/`,
    и без этого права push с такими изменениями отклоняется.

Добавьте его в секреты репозитория под именем **`RU_SYNC_TOKEN`**
(Settings → Secrets and variables → Actions → New repository secret).

Права `Issues` у PAT не нужны: issue создаётся обычным `GITHUB_TOKEN`.

### Почему конфликты возникают всегда

Апстрим добавляет новые локали (v2.0.4 принёс нидерландский), а форк добавляет
русский **в те же места**: тип `Locale` и массив `LOCALES` в `runtime.ts`, ключ
`common.language.*` в каждом словаре, блок локали в каждом модульном `*.i18n.ts`,
массивы локалей в модульных тестах. Git видит две правки одних и тех же строк и
останавливается — на каждом релизе.

Это не спор о содержании, поэтому `scripts/ru/resolve-merge-conflicts.mjs` разрешает
такие конфликты механически: берёт версию апстрима и заново накладывает русскую
часть. Всё, что скрипт не узнал, остаётся конфликтом — тогда релиз не выпускается и
создаётся issue.

Файлы с правками форка, которых скрипт не умеет переложить заново, он не трогает
вовсе — `KEEP_CONFLICTED` в резолвере: `ModelControls.tsx` (попап модели), `en.ts` и
`ru.ts`. Конфликт там останавливает синк и создаёт issue, тихой потери правок не
будет.

Отдельный случай — файл, который апстрим удалил, а форк успел перевести (так ушёл
`linear-integration.i18n.ts` в v2.5.1). У такой правки нет «версии апстрима», и
`git checkout --theirs` падает. Резолвер смотрит на стадии мержа и удаляет файл
вслед за апстримом, а `import` и спред, оставшиеся в `ru.ts` / `ru.settings.ts`,
убирают проходы `ensureRuModuleWiring` и `ensureRuSettingsModuleWiring`: они
сверяют список модулей с `en.ts` и `en.settings.ts`.

Два скрипта в `scripts/ru/` — это и есть вся «русская прослойка»:

| Скрипт | Что делает |
|---|---|
| `resolve-merge-conflicts.mjs` | разрешает конфликты локализации после мержа |
| `fill-missing-keys.mjs` | дополняет словари новыми ключами и убирает исчезнувшие |

### Модуль с компактной раскладкой

Не всякий модуль пишет по ключу на строку: `ui-blocks.i18n.ts` (v2.6.0) держит каждую
локаль одной длинной строкой. Оба скрипта понимают обе раскладки: `fill-missing-keys.mjs`
пересобирает `ru` в том же компактном виде, а `resolve-merge-conflicts.mjs` видит
компактный блок `ru` и не добавляет второй. Если синк упал на `no "en" block` для файла,
где блок явно есть, — значит апстрим придумал третью раскладку, и разбор в `localeRange`
нужен новый.

### Если синк не обновился

Workflow создаёт issue с меткой `ru-sync` (по одному на версию) и списком причин.
Дальше:

```bash
git checkout ru
git merge upstream/main      # или конкретный тег
# разрешить конфликты вручную, доперевести ключи
bun test packages/ui/src/lib/i18n
git push origin ru
```

и запустить workflow вручную с тем же `upstream_ref` — он проверит результат
и доведёт ветку до ума.

### Ручной запуск

Actions → **RU upstream sync** → Run workflow:

| Параметр | Что делает |
|---|---|
| `upstream_ref` | конкретный тег апстрима вместо последнего |
| `dry_run` | сделать всё, но не пушить ветку и не создавать issue |

### Где живёт файл workflow

`schedule` и `workflow_dispatch` GitHub выполняет только для файлов на ветке
**по умолчанию**, а здесь это `main`. Поэтому `ru-upstream-sync.yml` лежит и в `main`,
и в `ru` — копии должны совпадать. Релизный workflow раньше тоже зеркалили в
`main` (коммит `bf818cdb5`), чтобы пуш тега `ru-v*` запускал сборку; при переходе
на патчи копия удалена из обеих веток.

Из-за этого `main` больше не «чистое зеркало»: в нём лежат наши коммиты с
workflow. Синхронизировать `main` теперь нужно обычным мержем, а не `--ff-only`:

```bash
git checkout main
git merge upstream/main
git push origin main
```

### Гейт перед пушем

До `ru` не доходит сломанное слияние: `ru-upstream-sync.yml` после коммита
словарей запускает `node scripts/ru/verify-release-gate.mjs` и пушит ветку
только при зелёном гейте. Тот же скрипт гоняют руками перед накатом патча —
список проверок (локаль, fork-guards, `type-check:ui`)
живёт только в нём, в workflow лишь одна строка вызова.

Типы гейт проверяет через `bunx tsc -b`, а не `bun run type-check`: в корневом
`package.json` апстрима строка `bun check -b && …` ссылается на скрипт `check`,
которого нет ни в одном пакете. Свой CI апстрима её не запускает, поэтому
опечатка живёт. Локально вместо `bun run type-check` вызывайте `bunx tsc -b`.

## Сборка и установка русской версии вручную

Это основной путь: официальное приложение ставится из апстрима, русский интерфейс
собирается из ветки `ru` и подменяется скриптом поверх установленной копии.

Приложение для десктопа берёт интерфейс из папки `resources/web-dist` установленной
копии. Чтобы увидеть русскую версию, её нужно собрать из этой ветки и подменить.

```bash
cd openchamber
bun install
bun run --cwd packages/electron build:web-assets     # ~1.5 минуты
```

Готовый интерфейс окажется в `packages/electron/resources/web-dist`.

Дальше — скрипт `scripts/ru/install-desktop-locale.ps1`:

```powershell
# Закрыть OpenChamber, затем:
& ".\scripts\ru\install-desktop-locale.ps1" status    # что сейчас установлено
& ".\scripts\ru\install-desktop-locale.ps1" apply     # подменить (делает бэкап)
& ".\scripts\ru\install-desktop-locale.ps1" revert    # вернуть оригинал
```

Скрипт **не удаляет файлы** — только перезаписывает, потому что окружение блокирует
массовое удаление. Бэкап оригинала лежит рядом с `web-dist` в `web-dist.orig`.

### Нативные меню: патч main-процесса

`web-dist` покрывает только интерфейс внутри окна. Верхнее меню приложения и
меню значка в трее живут в main-процессе — `resources/app.asar` установленной
копии. Их патчит второй скрипт, тем же порядком и поверх того же установленного
приложения:

```bash
bun run --cwd packages/electron bundle:main     # секунды, не минуты
```

```powershell
# Закрыть OpenChamber, затем:
& ".\scripts\ru\install-desktop-main.ps1" status    # что сейчас установлено
& ".\scripts\ru\install-desktop-main.ps1" apply     # бэкап app.asar.orig + подмена
& ".\scripts\ru\install-desktop-main.ps1" revert    # вернуть оригинал
```

Правила те же, что у locale-патча, плюс три своих: версии установленного
приложения и ветки (`packages/electron/package.json`) обязаны совпадать — при
расхождении `apply` отказывается работать, смешивать main-бандл с чужим билдом
нельзя. Бэкап
`app.asar.orig` привязан к версии (`app.asar.orig.version`); бэкап без записи
версии скрипт усыновляет только после проверки, что он действительно непатченный
и совпадает с установленным приложением, иначе требует разобраться вручную.
Маркер `app.asar.ru-main-patch` хранит версию, коммит и SHA-256 трёх файлов
бандла. Состояния `status`: `PATCHED` (патч совпадает со сборкой ветки),
`OUTDATED` (патч стоит, но сборка ветки ушла вперёд, маркер старый или архив
меняли вручную), `STALE` (маркер есть, патча нет — обновление затёрло архив),
`ORIGINAL`. Замена архива идёт через проверенный staged-файл (сентинел +
совпадение числа файлов с оригиналом); при сбое установки скрипт сам
восстанавливает бэкап. Обновление приложения заменяет `app.asar` целиком,
`status` покажет `STALE`, дальше пересборка и `apply`.

### Про обновления приложения

Обновление OpenChamber **затрёт русский язык**: установщик заменит `web-dist` официальной
сборкой. Само по себе это не случится — в приложении `autoDownload = false` и
`autoInstallOnAppQuit = false`, обновление ставится только вручную.

После каждого обновления:

```bash
git checkout ru
git merge upstream/main      # разрешить конфликты как описано выше
bun install
bun run --cwd packages/electron build:web-assets
```

и снова `apply`. Скрипт сам скажет `STATE: STALE`, если маркер патча пережил обновление,
а интерфейс уже откатился.

### Что делать дальше

Форк теперь самостоятельный — его нужно просто поддерживать:

1. По мере выхода новых версий апстрима подтягивать их и пересобирать релиз —
   см. «Обновление до новой версии апстрима» и «Релизы».
2. Если апстрим добавил новые ключи локализации — допереводить их,
   см. «Конфликты в локали».
3. Репозиторные доки для апстрима не переводить: `AGENTS.md` прямо требует английский
   для материалов проекта. Переводы живут только здесь.
